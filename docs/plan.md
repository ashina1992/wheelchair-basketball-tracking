# 開発計画

最終更新: 2026-09-26

CLAUDE.md の「機能ロードマップ」を、実行できる単位(フェーズ・タスク・完了条件)に分解したもの。
実装を進める中で実態と合わなくなった箇所は随時書き換え、末尾の変更履歴に記録する。

## 前提

- 開発者は1人。工数は「人日(集中して作業できる1日)」で見積もる。カレンダー上の日程は稼働時間が決まり次第追記する
- ローカルはGPUなし(Ryzen 5 5625U)。推論・前処理はローカルCPUで行い、**学習は Google Colab / Kaggle の無料GPUを使う**
- 映像は YouTube の試合映像を画面録画したもの。学習・評価用データは**試合単位で train/val/test を分割**する(同じ試合のフレームが学習と評価の両方に入ると精度が過大評価されるため)
- 【ユーザー作業】と書いたタスクは、アカウントや手作業が必要なため開発者本人が行う(映像の録画、アノテーション、Colab での学習実行、クラウドへのデプロイ)。それ以外はツール・コード側で先に用意し、本人の作業結果を差し込むだけで動くようにしておく

## 現在地(2026-09-26)

**既製モデル(COCO)でパイプラインを最後まで通し、Web アプリとしてローカルで動く状態。** 残りは主に【ユーザー作業】。

## リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| ボール検出の精度が出ない(小さい、ブレる、遮蔽される) | P4 のすべての判定 | アノテーションでボールを重点的に増やす、高解像度で学習・推論、軌跡の補間、得点変化(OCR)との併用 |
| アノテーション工数が膨らむ | P2 が長引く | 既製モデルの出力を下書きにする(`prepare_dataset.py`)、苦手シーンを中心に追加する |
| 公式ボックススコアが入手できない試合がある | P4 の評価 | 入手できる試合を評価用に優先して選ぶ。なければ手動で数える |
| 会場ごとの校正の手間 | 新しい会場の映像を解析するたびに必要 | 1会場3枚で済む。自動化は P5 の改善項目 |
| 放送カメラが回転のみのモデルから外れる | P5 | ショット判定で別アングルを除外。照合できないフレームは座標変換しない |
| CPU推論が遅い(1分の映像に約6〜7分) | P8 | 解析済みデモを中心に公開、アップロード解析は先頭60秒に制限(`WBT_MAX_SECONDS`)、将来は ONNX 化 |
| YouTube利用規約 | P7・P8 | アップロードのみ対応。映像・学習データの画像を公開リポジトリに含めない |

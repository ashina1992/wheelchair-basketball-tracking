# 開発計画

最終更新: 2026-09-26

CLAUDE.md の「機能ロードマップ」を、実行できる単位(フェーズ・タスク・完了条件)に分解したもの。
実装を進める中で実態と合わなくなった箇所は随時書き換え、末尾の変更履歴に記録する。

## 前提

- 開発者は1人。工数は「人日(集中して作業できる1日)」で見積もる。カレンダー上の日程は稼働時間が決まり次第追記する
- ローカルはGPUなし(Ryzen 5 5625U)。推論・前処理はローカルCPUで行い、**学習は Google Colab / Kaggle の無料GPUを使う**
- 映像は YouTube の試合映像を画面録画したもの。学習・評価用データは**試合単位で train/val/test を分割**する(同じ試合のフレームが学習と評価の両方に入ると精度が過大評価されるため)

## P2 データセット作成とファインチューニング(→ M1)

データ収集・準備
- [ ] 試合映像を5試合程度集める(男女、会場、ユニフォーム色の組み合わせがばらけるように)。画面録画に広告が入らないようにする(入った場合は区間をカット)
- [ ] 広角ショットのフレームだけを選ぶ(P3 のショット判定の簡易版をここで作って流用する)
- [ ] 試合単位で train/val/test に分割(目安: 3試合 / 1試合 / 1試合)

アノテーション
- [ ] アノテーション指針 `docs/annotation_guide.md`: クラス(`player`=選手+車いす全体、`ball`、`rim`、`referee`)、箱の付け方、遮蔽時の扱い、ベンチ・観客は付けない
- [ ] ツールの決定(CVAT を第一候補)
- [ ] 既製モデルの出力を下書きとして読み込み、修正する方式で工数を減らす
- [ ] 第1弾: 約300枚(ボールは既製モデルがほぼ使えないため、広角ショットでのボールを重点的に確保する)

学習・評価
- [ ] Colab/Kaggle で YOLOv8(s を基本に n/m と比較)をファインチューニング。ボール向けに imgsz 1280 以上、タイル分割推論(SAHI等)も比較する
- [ ] test セットで評価: クラス別 mAP50 / mAP50-95、密集シーンでの player 再現率
- [ ] 同じ test セットで既製モデル(person→player として比較)との差分を示す
- [ ] 誤りを分析し、苦手なシーンを中心に約300枚を追加 → 再学習(2周目)
- [ ] 学習ログ・評価結果を `docs/02_dataset.md`、`docs/03_finetune.md` にまとめる

**完了条件**: 自前モデルが test セットで既製モデルを上回り、その根拠(指標・学習曲線・誤り例)が文書化されている

## P3 トラッキング・チーム識別・ショット判定

- [ ] ショット判定: 広角の試合ショットかどうか(クローズアップ、リプレイ、観客席、暗転、広告などを除外)。低い位置のサイドラインカメラ(フリースロー時等に使われる)を解析対象に含めるかもここで決める。まずはコートの床色の面積比などの簡易ルールで作り、足りなければ小さな分類器を学習する
- [ ] 選手トラッキング: ByteTrack(ultralytics 組み込み)。ショットが切り替わったらトラックをリセットする
- [ ] ボールトラッキング: 検出が途切れる区間を補間する(カルマンフィルタ等)
- [ ] チーム識別: player の胴体部分の色特徴をクラスタリングする(試合ごとに2チーム+審判)
- [ ] 評価: 30秒程度のクリップにトラッキング正解を付け、IDF1 / ID切り替え回数を測る

**完了条件**: 広角ショット区間で、選手ID・チーム・ボール軌跡が時系列データとして出力される

## P4 基本スタッツの自動検出(→ M2)

- [ ] スコアボードOCR: 試合時計・得点を読み取る(ラズパイでのOCR開発経験を活かせる)。イベントを試合時刻に対応付け、得点変化は成功シュートの手がかりと評価の両方に使う
- [ ] ボール保持者の推定(ボールと選手の位置関係、保持の継続時間)
- [ ] イベント判定:
  - シュート試投: ボールがリング方向へ上向きに離れる
  - シュート成否: リング付近を通過したか+得点変化
  - リバウンド: シュート失敗後に最初に保持したチーム・選手(攻守)
  - アシスト: 成功シュートの直前に同チーム選手からのパスがあったか
- [ ] リプレイ区間の除外(P3 のショット判定を利用)による二重カウントの防止
- [ ] 評価: 公式ボックススコア/プレーバイプレーを正解とし、イベント種別ごとの適合率・再現率を求める
- [ ] CLI: 動画を入力するとイベント一覧とスタッツ表(JSON/CSV)を出力する
- [ ] `docs/04_stats_detection.md` に判定ロジックと評価結果をまとめる

**完了条件**: 評価対象の試合で、シュート試投・成否を中心に精度が数値で示され、CLI で再現できる

## リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| ボール検出の精度が出ない(小さい、ブレる、遮蔽される) | P4 のすべての判定 | アノテーションでボールを重点的に増やす、高解像度で推論する、軌跡の補間、得点変化(OCR)との併用 |
| アノテーション工数が膨らむ | P2 が長引く | 既製モデルの出力を下書きにする、苦手シーンを中心に追加する方式にする |
| 公式ボックススコアが入手できない試合がある | P4 の評価 | 入手できる試合を評価用に優先して選ぶ。入手できない場合は手動で数えた正解で代替する |
| 動的ホモグラフィが安定しない | P5・P9 | 対象を広角ショットに限定、時間方向の平滑化、キーポイントが足りないフレームは補間する |
| CPU推論が遅く、Web公開で実用にならない | P8 | 解析済みデモを中心に公開する、推論間隔を間引く、ONNX 化で高速化する |
| YouTube利用規約(動画のダウンロードや再配布の制限) | P1・P7・P8 | 公開版で「YouTube URL を指定して取得・解析」を提供するかは P1 で判断する。学習データの画像や映像そのものを公開リポジトリに含めない |
